# UC-04: Sinh bài Reading / Listening đã kiểm chứng

Backend nhận kỹ năng, chủ đề, band mục tiêu và sinh bài mới. `UC04Agent` điều phối các agent sinh bài, giải độc lập và kiểm tra an toàn; mỗi bài được kiểm tra bằng code và solver trước khi lưu vào ngân hàng. Phạm vi hiện tại gồm API, script Listening, đáp án, trace; UC-05, giao diện người học và tổng hợp âm thanh nằm ngoài thay đổi này. Các UC được tổ chức thành module agent riêng theo [quy ước kiến trúc](architecture.md).

## Ranh giới tích hợp CSDL

Tuân thủ [DATABASE_CONTEXT.md](../DATABASE_CONTEXT.md): Reading/Listening tổ chức theo `CONTENT_ITEM → QUESTION_GROUP → QUESTION`, lưu kết quả kiểm định ở `VALIDATION_RESULT`. Hướng dẫn, loại câu, giới hạn trả lời và ngân hàng options dùng chung thuộc group; `body` chỉ chứa nội dung passage/script, không nhân bản nhóm và câu hỏi. Mỗi câu có một số câu và một nguồn đáp án; các câu bị loại vẫn cần được ghi nhận trong kết quả kiểm định.

Danh sách câu hỏi phẳng do LLM trả về là định dạng trao đổi nội bộ. Nó không thay thế cấu trúc lưu trữ theo nhóm. Ứng dụng chuẩn hoá nhóm trước khi xuất bản và không nhân bản ngân hàng lựa chọn chung xuống từng câu trong CSDL.

Người dùng đã chọn PostgreSQL chạy bằng Docker. [Schema UC-04](../backend/ielts_agent/infrastructure/db/sql/001_uc04.sql) là schema phát triển cho các thực thể đã rõ trong bản tóm tắt; đây không phải bằng chứng về cấu trúc CSDL triển khai ở hệ thống khác. Không suy diễn cấu trúc `EXAM`, `EXAM_ITEM`, `exam_item_id` hoặc `answer_sets` từ bản tóm tắt. UC-04 hiện chỉ sinh câu có một đáp án; các dạng Choose TWO letters/answer sets nằm ngoài phạm vi cho đến khi schema được xác nhận.

## Cài đặt và chạy

Cần Python 3.11 trở lên và Docker có Docker Compose. Ví dụ PowerShell:

```powershell
docker compose up -d --wait
python -m venv .venv
./.venv/Scripts/Activate.ps1
python -m pip install -e '.[dev]'
$env:DATABASE_URL = 'postgresql://ielts:ielts_dev_password@localhost:55432/ielts'
$env:OPENAI_API_KEY = 'your-api-key'
$env:PROVIDER = 'openai'
$env:GENERATOR_MODEL = 'gpt-4.1-mini'
python -m uvicorn ielts_agent.api.main:app --host 127.0.0.1 --port 8000
```

Mở `http://127.0.0.1:8000/docs` để thử API. Nếu không dùng lệnh kích hoạt môi trường, thay `python` bằng `./.venv/Scripts/python.exe`.

Ứng dụng tự nạp `.env` bằng `python-dotenv`; biến đã có trong shell được ưu tiên. Có thể sao chép [.env.example](../.env.example) thành `.env` rồi điền key. Không đưa API key vào Git hoặc payload HTTP. [compose.yaml](../compose.yaml) chạy PostgreSQL 17 với service `db`, healthcheck và volume giữ dữ liệu qua các lần khởi động. Cách vận hành PostgreSQL bằng container được mô tả trong [hướng dẫn Docker chính thức](https://docs.docker.com/guides/postgresql/). `DATABASE_URL` trỏ tới PostgreSQL qua cổng host **55432**, ánh xạ tới cổng container 5432; URL trong ví dụ dùng tài khoản phát triển của Compose. Nếu đổi `POSTGRES_PASSWORD` hoặc `POSTGRES_PORT` của Compose, cập nhật password/port tương ứng trong `DATABASE_URL` và `TEST_DATABASE_URL`.

API tự áp dụng các SQL migration còn thiếu trong `backend/ielts_agent/infrastructure/db/sql/` trước khi phục vụ request, mặc định `DATABASE_AUTO_MIGRATE=true`. Bảng `uc04_schema_migration` lưu phiên bản/checksum; file đã chạy được bỏ qua, dữ liệu hiện có được giữ. Docker Compose chỉ tạo database và giữ volume, không chạy SQL schema riêng. Có thể đặt `DATABASE_AUTO_MIGRATE=false` và chạy `python -m ielts_agent.infrastructure.db.cli init` thủ công. Không sửa file migration đã áp dụng; thêm file số tiếp theo để thay đổi schema. Xem [cơ chế migration](database-migrations.md). Dùng `docker compose down` để dừng môi trường và giữ volume.

### Dùng DeepSeek

DeepSeek cung cấp API tương thích OpenAI và hỗ trợ JSON mode, nên ứng dụng dùng chung OpenAI Python SDK. Xem [hướng dẫn API DeepSeek](https://api-docs.deepseek.com/) và [JSON Output](https://api-docs.deepseek.com/guides/json_mode/).

```powershell
$env:PROVIDER = 'deepseek'
$env:DEEPSEEK_API_KEY = 'your-deepseek-key'
$env:GENERATOR_MODEL = 'deepseek-flash'
python -m uvicorn ielts_agent.api.main:app --host 127.0.0.1 --port 8000
```

Có thể dùng một provider hoặc model khác cho solver:

```powershell
$env:SOLVER_PROVIDER = 'openai'
$env:SOLVER_MODEL = 'gpt-4.1-mini'
$env:OPENAI_API_KEY = 'your-openai-key'
```

Nếu không đặt `SOLVER_PROVIDER` và `SOLVER_MODEL`, solver dùng provider đã chọn và model mặc định của provider đó. Solver vẫn chạy trong lời gọi stateless riêng và không được nhận đáp án của generator. Model name có thể thay đổi theo tài khoản và dịch vụ; cấu hình lại model nếu provider thông báo model không khả dụng.

Ứng dụng dùng Chat Completions JSON mode để tương thích hai provider; JSON hợp lệ vẫn phải qua schema và validator. [Tài liệu OpenAI về JSON mode](https://developers.openai.com/api/docs/guides/structured-outputs) phân biệt bảo đảm cú pháp JSON với bảo đảm tuân thủ schema.

## API

### Sinh bài

`POST /api/exercises`

```json
{
  "skill": "reading",
  "topic": "Rừng ngập mặn Cần Giờ",
  "target_band": 6.0,
  "question_count": 10,
  "completion_word_limit": 2
}
```

`skill` nhận `reading` hoặc `listening`; band từ 1 đến 9 theo bước 0.5. `question_count` từ 8 đến 13, mặc định 10. Giới hạn Completion từ 1 đến 5 từ, mặc định 2. Với Listening, đổi `skill` thành `listening`; đầu ra là script 400–700 từ.

Ví dụ gọi bằng PowerShell:

```powershell
$request = @{
  skill = 'reading'
  topic = 'Rừng ngập mặn Cần Giờ'
  target_band = 6.0
  question_count = 10
  completion_word_limit = 2
} | ConvertTo-Json
$exercise = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8000/api/exercises' -ContentType 'application/json; charset=utf-8' -Body ([System.Text.Encoding]::UTF8.GetBytes($request))
$exercise | ConvertTo-Json -Depth 20
```

API trả **201** khi thành công. Đầu ra chứa `id`, `title`, `text`, `skill`, `topic`, `target_band`, `source=llm_generated_verified`, `status=verified`, `model`, `prompt_version`, `position`, `created_at`, `trace_id`, `validation` và `question_groups`.

| Vị trí | Trường chính |
|---|---|
| `validation` | `rules=true`, `solver=true`; trace chứa kết quả chi tiết và dedup |
| `question_groups[]` | `group_id`, `position`, `question_type`, `instructions`, `response_mode`, `options`, `response_limits`, `allow_reuse`, `questions` |
| `question_groups[].questions[]` | `id`, `position`, `number`, `prompt`, `options` riêng, `target`, `excluded` |

Hướng dẫn, loại câu, giới hạn trả lời và lựa chọn chung nằm tại group; câu hỏi riêng chứa từng vị trí trả lời. `number` là số câu hiển thị, còn `position` là thứ tự trong nhóm. Với Matching Headings, `target` chỉ đến paragraph thuộc item cha. Câu hỏi công khai không chứa đáp án, bằng chứng hoặc giải thích. Một số câu lỗi có thể bị loại, nên số câu cuối cùng có thể thấp hơn số yêu cầu nhưng luôn còn 8–13 câu và ít nhất ba dạng.

### Liệt kê bài trong kho đề

`GET /api/exercises` trả **200** cùng danh sách tóm tắt bài Reading/Listening.
Endpoint dùng bearer và cơ chế xử lý lỗi CSDL hiện có; không gọi agent sinh bài.

| Query | Giá trị |
|---|---|
| `skill` | Không bắt buộc; `reading` hoặc `listening` viết thường |
| `target_band` | Không bắt buộc; từ 1 đến 9 theo bước 0.5, lọc đúng band |
| `q` | Mặc định rỗng; tối đa 200 ký tự, không chứa NUL. Bỏ khoảng trắng hai đầu, tìm chuỗi con trong tiêu đề hoặc chủ đề, không phân biệt hoa/thường. `%` và `_` là ký tự thường |
| `limit` | Số bài mỗi trang; mặc định 20, từ 1 đến 100 |
| `offset` | Số bài bỏ qua; mặc định 0, từ 0 đến 2147483647 |

Ví dụ: `GET /api/exercises?skill=reading&target_band=6&q=mangroves&limit=20&offset=0`.

```json
{
  "items": [
    {
      "id": "5b0c2a7e-1f4d-4c8a-9d3e-2a6b7c8d9e0f",
      "title": "Mangroves",
      "skill": "reading",
      "topic": "Can Gio mangroves",
      "target_band": 6.0,
      "source": "llm_generated_verified",
      "status": "verified",
      "created_at": "2026-11-11T03:00:00Z",
      "question_count": 10,
      "question_types": [
        "multiple_choice",
        "sentence_completion",
        "true_false_not_given"
      ]
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

`total` đếm toàn bộ bài khớp bộ lọc trước phân trang. Không có kết quả trả
`items=[]`, `total=0`; offset vượt trang cuối vẫn trả tổng đúng và danh sách rỗng.
Thứ tự là `created_at` giảm dần, sau đó UUID bài giảm dần khi trùng thời điểm.
`question_types` chứa các dạng câu duy nhất, sắp theo tên; `question_count` là
tổng số câu của bài.

Chỉ bài `verified` của Reading/Listening, không có câu bị loại và có đủ ba lớp
`rules`, `solver`, `dedup` cùng mọi kết quả kiểm định đạt mới được liệt kê. Danh
sách không chứa passage/script, câu hỏi chi tiết, đáp án, bằng chứng, giải thích,
model hoặc trace. Dùng endpoint theo UUID bên dưới để lấy nội dung bài.

Frontend có thể gọi cùng query qua `GET /api/backend/exercises`; proxy chuyển
tiếp đến backend và thêm bearer phía server khi cấu hình. Màn kho đề hiện vẫn
dùng dữ liệu mẫu; thay nguồn dữ liệu của UI là bước tích hợp riêng. Query không
hợp lệ trả `422`; thiếu/sai bearer khi bật `API_TOKEN` trả `401`; PostgreSQL hoặc
schema chưa sẵn sàng trả `503` với mã `database_unavailable`.

### Đọc bài, đáp án và trace

| Endpoint | Nội dung |
|---|---|
| `GET /api/exercises/{id}` | Văn bản và các nhóm/câu hỏi công khai của bài đã kiểm chứng |
| `GET /api/exercises/{id}/answers` | Đáp án, evidence span và giải thích |
| `GET /api/traces/{trace_id}` | Kết quả safety, hai lớp validator, loại câu, thử lại và kiểm tra trùng |

Endpoint đáp án trả `item_id` và `answers[]`; mỗi phần tử có `question_id`, `number`, `answer_key`, `evidence_span`, `explanation`. ID trong đáp án là ID câu đã lưu, không phải ID tạm do generator đặt. `GET /health` trả trạng thái tiến trình, không thực hiện kiểm tra kết nối PostgreSQL.

Trace bao gồm các lần ứng viên thất bại và lần được chấp nhận, giúp kiểm tra bài đã qua cả hai lớp. Bài chưa được chấp nhận không xuất hiện ở endpoint phát bài.

### Mã lỗi

| HTTP | Ý nghĩa |
|---|---|
| 400 | Chủ đề được yêu cầu bị đánh giá không phù hợp |
| 401 | Thiếu hoặc sai bearer token khi bật `API_TOKEN` |
| 404 | Không tìm thấy bài hoặc trace |
| 422 | Request sai hoặc không tạo được bài đạt chuẩn sau số lần thử cho phép |
| 503 | Thiếu cấu hình provider, lỗi API, hoặc không lấy được kết quả kiểm chứng đáng tin cậy |

Lỗi sinh bài có mã trace để tra cứu nguyên nhân khi trace đã được tạo. Không đưa thông báo chứa API key hoặc nội dung lỗi thô của provider vào phản hồi.

Mặc định chạy cục bộ. Có thể đặt `$env:API_TOKEN = 'a-long-random-token'` để yêu cầu `Authorization: Bearer ...` trên các route bài và trace. Token dùng chung này không thay thế hệ thống tài khoản hay phân quyền từng người học; endpoint đáp án và trace dành cho công cụ quản trị/đánh giá trong phạm vi backend hiện tại.

## Luồng kiểm chứng

1. `ContentSafetyAgent` kiểm tra độ phù hợp của chủ đề trước khi sinh. Kiểm tra toàn bộ ứng viên, gồm đáp án và giải thích, trước khi phát.
2. `ItemGenerationAgent` dùng [skill `reading-item-generation`](../backend/ielts_agent/agents/uc04/skills/reading-item-generation/SKILL.md), tạo passage/script cùng câu hỏi và đáp án. Trace ghi prompt version và hash nội dung skill.
3. Code kiểm tra Reading 600–900 từ, Listening 400–700 từ, 8–13 câu, ít nhất ba dạng, ID duy nhất và hợp đồng từng dạng câu.
4. Completion phải chép nguyên văn một cụm từ trọn vẹn từ văn bản và bằng chứng, không vượt giới hạn. Evidence của câu có đáp án xác định phải là substring chính xác trong bài. `NOT GIVEN` phải có evidence null; việc không có bằng chứng khẳng định/phủ định được solver kiểm tra ngữ nghĩa trên toàn văn.
5. `BlindSolverAgent` chỉ nhận văn bản, câu hỏi và lựa chọn công khai. Solver tự trả lời và tự trích bằng chứng. Thiếu ID, ID trùng, JSON lỗi hoặc provider lỗi không được coi là đã kiểm chứng. Câu không khớp đáp án bị đánh dấu và loại. Với câu giữ lại có đáp án khớp, bài công bố dùng bằng chứng và giải thích solver tự tạo, đã được kiểm tra nguyên văn và ràng buộc đúng loại câu; `NOT GIVEN` vẫn có evidence null. Safety kiểm tra lại bài cuối gồm các giải thích của solver trước khi lưu.
6. Loại **hơn 20%** câu thì sinh lại toàn bộ. Loại đúng 20% vẫn có thể tiếp tục nếu bài còn đủ số câu và dạng. Kiểm tra lại cấu trúc sau khi loại. Tối đa hai lần sinh lại, tức ba ứng viên tính cả lần đầu; hết lượt thì trả lỗi.
7. So sánh bài mới với ngân hàng trước khi lưu; việc kiểm tra và thêm bài cần nằm trong cùng transaction của adapter lưu trữ. Cosine similarity của vector tần suất token **lớn hơn 0.9** bị từ chối. Metric này là baseline trùng lặp từ vựng, chưa bảo đảm phát hiện mọi trường hợp diễn đạt lại cùng nội dung.

Chỉ bài vượt toàn bộ cổng kiểm tra mới có source `llm_generated_verified`. Metadata lưu generator/solver model, prompt version và kết quả validator. Tên source mô tả đáp án đã được pipeline kiểm chứng, không có nghĩa mọi tuyên bố thực tế trong bài đã được đối chiếu với nguồn bên ngoài.

## Kiểm thử và đánh giá

Tạo CSDL kiểm thử riêng một lần, sau đó chạy pytest:

```powershell
docker compose exec db psql -U ielts -d postgres -c "CREATE DATABASE ielts_test;"
$env:TEST_DATABASE_URL = 'postgresql://ielts:ielts_dev_password@localhost:55432/ielts_test'
python -m pytest
```

Bộ test model dùng fake agent và HTTP mock, không cần key hoặc gọi API có tính phí. Test tích hợp lưu trữ cần PostgreSQL đang chạy và `TEST_DATABASE_URL` trỏ tới CSDL kiểm thử riêng; không dùng CSDL chứa bài thật cho test. Các tình huống tối thiểu gồm Reading band 6.0 đủ ba dạng, Listening Completion hai từ, đáp án T/F/NG cố ý sai, Completion vượt giới hạn và chủ đề không phù hợp. Kiểm thử còn kiểm tra solver không thấy key, biên loại 20%, hết lượt thử và chống trùng ngân hàng. Endpoint `/answers` chỉ truy xuất key đã kiểm chứng; luồng nhận bài làm và chấm điểm nay được triển khai trong [dịch vụ luyện Reading/Listening riêng](reading-listening-practice.md), qua `/api/exercises/{id}/attempts` và `/api/attempts/{id}`. API sinh bài, key và trace hiện có giữ nguyên contract.
